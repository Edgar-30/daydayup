# 每日协作与验收

## 启动与执行

用户说“开始今天的任务”时，先读取 PROGRESS 和最近开发记录，确认昨日阻碍与今日时间；没有新时间信息时暂按 60 分钟，并明确这是沿用预算。

每天输出一个主要目标、最多两个配套任务和时间不足的最小版本。每项写明具体动作、岗位价值、预估时间、交付物和可执行验收。生成当天独立完整的 Codex 提示词，包含仓库、必读说明、范围、约束、预期行为、检查和汇报要求。

流程：制定任务 → Codex 实施并自检 → 用户阅读与亲自验证 → 提交成果 → 验收复盘。

用户已授权 Codex 正常提交与上传本仓库成果，因此实现完成并通过相关检查后可以发布；个人理解仍单独等待用户验收。只提交有意义的代码、测试或文档进展，不制造空提交、不倒签、不强制每日新增功能。

## 交作业模板

```text
日期：
今日目标：
实际完成：
commit / PR 链接或变更摘要：
验证命令与结果：
演示或截图（如适用）：
我能解释的一个技术点：
我亲自完成或验证的部分：
遇到的问题：
实际耗时：
下次可投入时间：
```

## 验收规则

- 通过：主要目标达到明确验收标准，有可核对证据。
- 部分通过：已有可用成果，但部分标准或理解验证未完成。
- 待补充：缺少足够信息，无法判断。

成果完成度和用户理解分别给结论。工具实际输出、可访问的提交和用户实际回答属于可核对证据；只有“测试通过”的总结而无可核对结果属于自述。Codex 的测试不代表用户独立完成。

每次验收最多列三个优先改进项，再问两个当天实现问题，等待回答后反馈。更新 PROGRESS；没有历史就索取最新摘要，不补写过去。未完成时缩减范围或拆解阻碍，下一天不叠加债务。

## 每周复盘

1. 新增了哪些可以演示、可以验证的能力？证据在哪里？
2. 陌生人按 README 能否运行，错误是否易理解？
3. 目标岗位哪些能力仍缺少证据？
4. 哪些关键代码用户还无法独立解释？
5. 下周继续、删减、调整什么？

按实际成果更新 README、演示和版本说明。简历内容必须有代码／验证证据与个人理解支撑，不编造数据、商业成果或团队经历。
